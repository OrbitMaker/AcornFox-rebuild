# AcornFox macOS native entry

This package targets Apple Silicon and macOS 13 or later. The managed Ubuntu ARM guest uses Virtualization.framework, 2 vCPU, 4 GiB memory, NAT, EFI, a persistent machine identifier, a virtio socket device, and a private sparse 40 GiB RAW disk. No host home directory is shared with the guest.

## State and recovery

The NAT adapter receives an explicit locally administered unicast MAC deterministically derived from the verified persistent instance UUID (`acornfox-virtio-network-v1`). Rebuilding the same VM configuration does not assign another random interface identity. This does not migrate the cloud-init network configuration of earlier random-MAC test instances; those failed test states must remain preserved, and the corrected configuration is accepted as a new first installation. Real same-instance reboot connectivity still needs runtime evidence.

All mutable host state resides in owner-only 0700 directories. File operations reject symlinks, unexpected owner/mode, and multiple hardlinks. `DiskPreparer` holds the cross-process instance lock until released; the controller retains it through VM shutdown. The base is streamed through gzip with compressed/raw digest and length checks, expanded only on first creation, synced, and published with exclusive rename. Registered user disks are validated by durable owner/device/inode/size and are never rehashed as the base.

Disk and EFI preparation have durable journals and bounded recovery. The EFI creator runs only inside a durably registered exclusive temporary namespace. Ready state is synced before exclusive publication; final identity is checked before journal removal. Unknown files and directories are retained. Metadata or published-file corruption is an error, not permission to reset it.

The seed is atomically published as a private directory containing its receipt, Ed25519 SSH identity, cloud-init source, and CIDATA ISO. Only `user-data` and `meta-data` enter the ISO. The private SSH key remains a 0600 host file. During first installation, new seed creation uses the verified bootstrap resources and current template. An authorized unfinished attempt reopens an existing supported seed using the persisted manifest fingerprint and file receipts; it does not guess an old template from new App code. After installation, `openExisting` validates only the persisted seed receipt, file digests, instance identity and supported instance protocol; it does not read the current App template or resources. `/usr/bin/ssh-keygen` and `/usr/bin/hdiutil` supply the native key and ISO implementation.

`host-installation.json` is the single host installation record. Its `preparing` form is atomically persisted before disk or seed creation and pins the exact eight-resource manifest. This authorizes only the same unfinished first-install attempt. Actual guest verification plus a fresh valid setup response are required before its atomic transition to `ready`; that initial receipt captures immutable bootstrap binding/helper/release facts and seed/disk/machine/EFI/known-host identities. A ready receipt is reused, never rebased to another backend. Atomic publication means process interruption leaves a complete preparing or ready record; unpublished temporary files are preserved.

A pre-existing disk/seed without this record, a corrupt record, or a pre-release seed without the supported protocol is refused. It is not treated as a fresh installation. No legacy instance is silently adopted or reset.

## Guest control and transport

The guest bridge runs as `com.acornfox.guest-bridge.service`. This desktop infrastructure name deliberately sits outside the backend's closed `acornfox-*` systemd inventory. The backend whitelist remains strict: the former `acornfox-guest-bridge.service` is an unknown managed unit and must still be rejected. The host-scope regression reads the actual Swift seed unit declaration and validates it against the production scope checker.

Changing this unit name changes the generated seed template and its input receipt. An existing owned seed with the old namespace is rejected without rewriting its ISO, SSH identity or receipt. Acceptance with this template and a later backend candidate is a new first installation after separately retaining the failed test state; it is not evidence of an old-instance upgrade or automatic recovery.

Cloud-init creates the `af-host` control account. Password login and root SSH are disabled. Sudo is restricted to `/usr/local/sbin/acornfox-desktop-control`; this root-owned dispatcher accepts only fixed identity/upload/install/verify/setup-code/shutdown operations plus an explicit bounded diagnostic log read. It validates the instance owner and the six package candidates against their seeded digests. Container applications receive no host filesystem share or host login key.

The host binds 127.0.0.1:8080 to guest virtio port 18080, and a random loopback SSH port to guest virtio port 22022. A bounded 32-connection pool forwards exact bytes with 64 KiB buffers and propagates half-close. It never kills an occupying process or selects arbitrary target ports. All VZ lifecycle/socket calls run on the configured VZ queue; network pumps own and close duplicated descriptors on their serial network queue.

Fresh installation streams the six resources over SSH and calls the fixed dispatcher. Root-owned installation journals distinguish a matching resumable attempt from an unknown partial installation or completed instance. Complete verified unpacked assets are reused. Installer stdout/stderr remain in guest `/var/lib/acornfox-desktop/install.log` with mode 0600. The fixed `install-log` operation returns at most the last 64 KiB only for explicit operator diagnostics; the GUI never requests or displays it. A completed instance uses only the fixed zero-argument `verify-current` operation. That operation checks the current root-owned helper using `contract-check`, the current runtime receipt and zero-argument read-only `verify-prepared`, without comparing the current helper/binding to the bootstrap config. Identity lookup creates no lock, and `verify-current` requires the existing control lock instead of repairing a missing one. The host compares this evidence with a trusted `InstalledInstanceContext` and makes a fresh setup probe. Failure never falls through to upload, install or recovery; the historical config and optional PI services are not reset.

Without an update authority, the expected backend binding is always the initial ready receipt's fixed value. `InstalledContextAuthority` is only a bridge interface: this package has no production implementation and accepts no CLI or raw snapshot override. A future adapter must validate a live opaque `HostStartupBasis`/authenticated IPC response and slot seal, including the instance/protocol. The authority is rechecked before and after probing and closed when `openInstalled` ends; closed or changed leases cannot authorize a cached binding. No Go controller/update state machine is implemented here.

After SSH identity is confirmed, the host registers a shutdown request for that exact VM run. It uses a fresh short-lived SSH scope independent of installer cancellation, rechecks the instance owner, and invokes only the fixed `shutdown` verb. The root-owned guest dispatcher accepts no additional arguments and executes `/usr/bin/systemctl --no-block poweroff`. An SSH success or `shutdown_requested` reply does not release the VM: only the VZ guest-stopped event confirms shutdown. A rejection or 90-second timeout retains the VM, forwarding and disk lock, with no force-stop fallback. Before SSH is available, the host retains the VZ power-button request/timeout policy. Older seeds without this verb are not rewritten; this capability belongs to the new first-install template.

Native startup checks require a helper that supports `verify-prepared` (the next candidate generation, beta.17 or later). `recover-finalize` is not a substitute: its upgrade-recovery pre-dispatch may modify an in-flight transaction. The new command goes directly to prepared-state verification after the normal identity/root gates. Earlier packages, including V6 with beta.16, remain historical test artifacts; changing the initial control template is not an in-place upgrade of an old seed.

The GUI does not interpret VM running as application readiness. A fresh, nonredirected, bounded setup GET must return exactly an initialized/uninitialized state before Open is enabled, and every Open action probes again. Copy Setup Code is explicit, probes again, and transfers the code directly to the clipboard without putting it in logs, disk status or URLs.

## Packaging and verification

`build-app.sh` copies the actual base and flat six-file candidate, builds the ARM guest bridge, computes exactly eight resource digests and obtains the bootstrap helper digest from the ARM archive. It writes the manifest itself and compiles all Swift sources into an ad-hoc signed app. Its legacy `--resource-root` argument remains accepted for invocation compatibility; a handwritten manifest is no longer consumed.

Run `bash desktop/macos/Tests/run-tests.sh` from this checkout for actual Swift disk/EFI/seed/network/probe tests, guest-script recovery tests, native helper argv-contract/golden-response checks and app source compilation. The tests use real gzip, ssh-keygen, hdiutil, VZ EFI file creation, socketpair/loopback transport, and SIGKILL recovery. They never start a VM or open the desktop. Mock install effects prove the dispatcher state machine, not a real package installation.

Headless acceptance can compile every `Sources/*.swift` except `main.swift` with a task-owned `@main` runner. Create `DiskPreparer` and `InstalledReceiptStore(directory: preparer.vm, instance: preparer.instanceID)`. If `load()?.phase == "ready"`, obtain `context()`, validate it to retrieve the saved seed and call `openExistingDisk()`; do not construct current `Resources`. Otherwise verify the strict resources, call `authorizeBootstrap(manifest:)` **before** `prepare(gzip:manifest:)` or `prepareSeed`, and pass those resources to the provisioner.

Retain `VMController`, start with the prepared/saved seed, and keep the main run loop alive. On its original `.running(run)` callback, create `Provisioner(running: run, resources: optionalBootstrapResources, state: preparer.vm)`. For a ready context call `openInstalled(context:onAuthenticated:progress:)`; otherwise call `prepare(onAuthenticated:progress:)`, which writes ready only after installation evidence and fresh setup succeed. In the authenticated callback register `controller.useAuthenticatedShutdown(for: run, request: provisioner.makeShutdownRequest())`. For stopping, cancel the provisioner then use `stop(failure:completion:)`; failure keeps the controller/process alive and only completion permits exit. Sign a headless runner before a real VM start.

Real guest boot, SSH reachability, package install, public browser/customer acceptance, Developer ID signing, and notarization require separate evidence. Background headless acceptance is not a GUI pass.
